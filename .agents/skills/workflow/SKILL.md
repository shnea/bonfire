# workflow

프로젝트 기준의 확인·갱신은 [golden_path](../golden_path/SKILL.md)를 따른다.

## 1. 목적과 실제 상태 확인

- 요청의 목적, 기존 코드와 변경 사항, 이번 작업 범위를 파악한다. 합의한 작업 범위 안에서 진행한다.
- 사용자의 제안도 목적에 비춰 검토한다. 과한 구조·중복·불필요한 절차가 보이면 이유와 더 단순한 대안을 제시하고 함께 정리한다. 명확히 정한 요구·제약을 임의로 바꾸지는 않는다.

## 2. 필요한 만큼 함께 결정

- 새 프로젝트는 목적·사용자·핵심 흐름·이번 범위부터 정리한다. 이미 답했거나 코드에서 확인할 수 있는 내용을 다시 묻지 않는다.
- 정보가 꼭 필요하거나 요구가 충돌하는 부분만 짧게 질문한다. 맡겨진 선택은 판단해서 진행하고 관련 없는 작업까지 멈추지 않는다.
- 다음 구현의 범위·완료 조건·필수 선택이 준비되면 진행한다. 모든 항목의 완성과 별도 시작 승인을 요구하지 않는다. 정의·검토만 요청받았다면 그 범위를 지킨다.
- 작업 규모에 맞춰 바꿀 부분과 확인 방법을 정한다. 작은 수정에 별도 계획 문서·독립 리뷰·병렬 작업을 자동으로 추가하지 않는다.

## 3. 구현

- 기존 코드·표준 라이브러리·플랫폼 기능으로 요구를 충족하는 단순한 구현을 우선한다. 정확성·보안·접근성·필요한 검증은 유지한다.
- 실제 코드와 문서가 다르면 원인을 확인한다. 어느 한쪽을 무조건 맞는 것으로 간주하지 않는다. 중요한 결정·요구 변경은 golden_path에 반영한다.
- 다른 작업의 변경을 보존하고 비밀값을 소스·일반 문서에 넣지 않는다.
- 데이터 삭제·강제 덮어쓰기 등 되돌리기 어렵거나 손실 가능성이 있는 작업은 명시된 요청·위임 범위에서만 수행한다. 범위가 불명확하면 실행 전에 확인한다.
- 외부 반영·커밋·푸시·배포는 현재 사용자 요청과 기존 위임 범위에서 진행한다. 이미 받은 권한은 반복해서 묻지 않고, 기존 변경이라는 이유만으로 커밋에서 기계적으로 제외하지 않는다.

## 4. 검증과 인계

- 프로젝트의 필수 검사와 변경 영향에 맞는 검증을 실행한다. 실패 원인을 고친 뒤 관련 검증을 다시 확인하되, 새 근거 없이 같은 검사·미세 조정을 반복하지 않는다.
- 배포를 수행했다면 정해진 성공 확인까지 한다. 스킬 연결처럼 준비 확인과 실제 실행이 다른 작업은 결과를 구분한다.
- 바뀐 내용, 실제 검증 결과, 미실행·실패·남은 사항을 정확히 보고한다. 진행 중 새 요구가 생기면 필요한 결정부터 다시 정리한다.
